# cf-cdn-js-validator (Validator V3)

## Available Tools

You have these tools: `read`, `write`, `shell`, `code`. Use `read` for reading files and listing directories. Use `shell` for running validation commands (`node --check`, `wc -c`) and listing directories.

---

Validates ALL JavaScript files generated for a domain's CloudFront Functions
and Lambda@Edge handlers. This is a pure validation pass — it reports failures
but **never modifies files** and **never suggests fixes**.

---

## Adversarial Posture

> **Default assumption: every file is broken until proven otherwise.**

- Find failures. Do NOT confirm success unless every single check passes.
- Fail on ambiguity. When in doubt, FAIL.
- No fix suggestions. Report the failure and stop.
- False negative (missing a real bug) is **worse** than false positive (flagging
  something benign). When uncertain, flag it.
- Never re-generate, edit, patch, or suggest patches for failing files.
- A single FAIL in any file marks the entire domain validation as FAILED.

---

## Path Resolution

All paths are relative to the current working directory when the skill is invoked.

| Logical name | Resolved path |
|---|---|
| CFF functions dir | `cloudflare-to-aws-cdn/terraform/domains/<sanitized-hostname>/functions/` |
| Lambda dir | `cloudflare-to-aws-cdn/terraform/domains/<sanitized-hostname>/lambda/` |
| Domain IR | `cloudflare-to-aws-cdn/ir/final/<hostname>.json` |
| Output JSON | `cloudflare-to-aws-cdn/ir/validation/js/<hostname>-v3.json` |

`<hostname>` is the raw hostname (e.g., `cdn.c.example.com`).
`<sanitized-hostname>` replaces every `.` and `-` with `_` (e.g., `cdn_c_example_com`).

cloudflare-to-aws-cdn/ir/validation/js/

Create the directory if it does not exist.

## Output JSON Schema

```jsonc
{
  "schema_version": "v3",
  "hostname": "<hostname>",
  "timestamp": "<ISO-8601 UTC>",
  "overall_status": "PASS" | "FAIL",
  "files": [
    {
      "file": "<relative path from workspace>",
      "type": "cloudfront_function" | "lambda_edge",
      "status": "PASS" | "FAIL",
      "checks": [
        {
          "check_id": "<CHECK_ID>",
          "description": "<human-readable description>",
          "status": "PASS" | "FAIL" | "SKIP",
          "detail": "<evidence: line numbers, grep output, byte count, etc.>"
        }
      ]
    }
  ]
}
```

`overall_status` is `FAIL` if ANY file has `status == "FAIL"`.
`overall_status` is `PASS` only if ALL files have `status == "PASS"` AND at
least one file was validated (an empty domain is itself a FAIL — see Step 2).

## Workflow

### Step 0 — Read reference documents first

Before running any checks, read:

1. `~/.kiro/skills/cloudflare-aws-converter/cf-cdn-js-validator/references/unsupported-syntax.md` — tested forbidden ES6+ features.
2. `~/.kiro/skills/cloudflare-aws-converter/cf-cdn-js-validator/references/validation-checklist.md` — complete validation checklist.
3. The domain's IR: `cloudflare-to-aws-cdn/ir/final/<hostname>.json`
   — to understand whether Lambda@Edge escalation was expected, whether KVS is
   in use, and which ops should be present.

If the IR file is missing, record it as a prerequisite failure in the output
JSON under a synthetic file entry with type `"prerequisite"` and halt.

---

### Step 1 — Discover files

Enumerate all `.js` files under:
- `cloudflare-to-aws-cdn/terraform/domains/<sanitized-hostname>/functions/`
- `cloudflare-to-aws-cdn/terraform/domains/<sanitized-hostname>/lambda/`

where `<sanitized-hostname>` = raw hostname with every `.` and `-` replaced by `_`.

Use:
```bash
find "<functions_dir>" -name "*.js" -type f 2>/dev/null
find "<lambda_dir>" -name "*.js" -type f 2>/dev/null
```

Classify each file:
- Files in `functions/` → type `cloudfront_function`
- Files in `lambda/` → type `lambda_edge`

If both directories are absent or empty, record:
```json
{
  "check_id": "DISCOVERY",
  "description": "At least one JS file must exist for the domain",
  "status": "FAIL",
  "detail": "No .js files found in functions/ or lambda/ directories"
}
```
Set `overall_status = "FAIL"` and write output. Do not proceed.

---

### Step 2 — Validate CloudFront Function files

For each file classified as `cloudfront_function`, run ALL of the following
checks in order. Collect results; do NOT stop at the first failure — run every
check and report all failures.

#### CHECK CFF-01: Syntax check

```bash
node --check "<file_path>"
```

- Capture exit code and stderr.
- `status`: `PASS` if exit code == 0, `FAIL` otherwise.
- `detail`: include full stderr output on FAIL.

#### CHECK CFF-02: Optional chaining

```bash
grep -n '\?\.' "<file_path>"
```

- `status`: `FAIL` if grep returns any output (exit code 0 means lines found).
- `detail`: include all matching lines with line numbers on FAIL.
- Note: `?.` is forbidden in CloudFront Functions Runtime 2.0.

#### CHECK CFF-03: Array destructuring

```bash
grep -n 'const \[' "<file_path>"
grep -n 'let \[' "<file_path>"
```

- `status`: `FAIL` if either grep returns any output.
- `detail`: include all matching lines on FAIL.

#### CHECK CFF-04: Object destructuring

```bash
grep -n 'const {' "<file_path>"
grep -n 'let {' "<file_path>"
```

- `status`: `FAIL` if either grep returns any output.
- `detail`: include all matching lines on FAIL.

#### CHECK CFF-05: Promise usage

```bash
grep -n 'Promise\.' "<file_path>"
```

- `status`: `WARN` if grep returns any output (not FAIL — Promise methods are
  syntactically valid in Runtime 2.0 but risk exceeding memory quota per AWS docs).
- `detail`: include all matching lines on WARN, with note: "Promise combinators
  are syntactically valid but AWS warns they may exceed function memory quota.
  Use sequential await instead."
- This catches `Promise.all`, `Promise.any`, `Promise.race`, `Promise.resolve`,
  `Promise.reject`.

#### CHECK CFF-06: File size limit

```bash
wc -c < "<file_path>"
```

- `status`: `FAIL` if byte count > 8192.
- `detail`: `"File size: <N> bytes (limit: 8192)"`.
- Hard limit for CloudFront Function code package.

#### CHECK CFF-07: Import statement (conditional)

```bash
grep -n 'cf\.kvs\|cf\.updateRequestOrigin\|cf\.edgeLocation' "<file_path>"
```

- If any of these `cf.*` API calls are present in the file, then the first line
  MUST be `import cf from 'cloudfront'`.
- If none of these calls are present, the import is optional — skip this check.
- `status`: `FAIL` only if `cf.*` API is used but the import is absent.
- `detail`: include the actual first line and the found `cf.*` usage on FAIL.

#### CHECK CFF-08: Handler signature

```bash
grep -n 'async function handler(event)' "<file_path>"
```

- `status`: `FAIL` if grep returns no output (exit code 1 = not found).
- `detail`: `"Handler signature 'async function handler(event)' not found"` on FAIL.

#### CHECK CFF-09: Return statement

Run all four greps:
```bash
grep -n 'return req' "<file_path>"
grep -n 'return request' "<file_path>"
grep -n 'return response' "<file_path>"
grep -n 'return {statusCode' "<file_path>"
```

- `status`: `FAIL` if ALL FOUR greps return no output (none found).
- A file with no return is an invalid handler.
- `detail`: `"No valid return statement found (checked: 'return req', 'return request', 'return response', 'return {statusCode')"` on FAIL.

#### CHECK CFF-10: No `.then` / `.catch` chains

```bash
grep -n '\.then(' "<file_path>"
grep -n '\.catch(' "<file_path>"
```

- `status`: `WARN` if either grep returns any output (not FAIL — `.then()` and
  `.catch()` are syntactically valid in Runtime 2.0 but risk exceeding memory
  quota per AWS docs).
- `detail`: include all matching lines on WARN, with note: "Promise chain methods
  are syntactically valid but AWS warns they may exceed function memory quota.
  Use sequential await instead."

---

### Step 3 — Validate Lambda@Edge files

For each file classified as `lambda_edge`, run ALL of the following checks:

#### CHECK LE-01: Syntax check

```bash
node --check "<file_path>"
```

- `status`: `PASS` if exit code == 0, `FAIL` otherwise.
- `detail`: include full stderr on FAIL.

#### CHECK LE-02: Handler export pattern

```bash
grep -n 'exports\.handler' "<file_path>"
```

- `status`: `FAIL` if grep returns no output.
- Lambda@Edge must use CommonJS format (`exports.handler`).
- `detail`: `"No valid handler export found (checked: 'exports.handler')"` on FAIL.

#### CHECK LE-03: File size limit

```bash
wc -c < "<file_path>"
```

- `status`: `FAIL` if byte count > 1048576 (1 MB).
- `detail`: `"File size: <N> bytes (limit: 1048576)"` on FAIL.

#### CHECK LE-04: No cloudfront import

```bash
grep -n "import cf from 'cloudfront'" "<file_path>"
grep -n 'require("cloudfront")' "<file_path>"
grep -n "require('cloudfront')" "<file_path>"
```

- `status`: `FAIL` if ANY grep returns output.
- The `cloudfront` module does not exist in Lambda@Edge runtime.
- `detail`: include all matching lines on FAIL.

#### CHECK LE-05: Lambda event shape

```bash
grep -n 'event\.Records\[0\]\.cf' "<file_path>"
```

- `status`: `FAIL` if grep returns no output.
- Lambda@Edge must use `event.Records[0].cf` to access the CloudFront request,
  not `event.request` (which is the CloudFront Functions shape).
- `detail`: `"Lambda@Edge must use event.Records[0].cf.request — 'event.Records[0].cf' not found"` on FAIL.

#### CHECK LE-06: Callback or return present

```bash
grep -n 'callback(null' "<file_path>"
grep -n 'return ' "<file_path>"
```

- `status`: `FAIL` if BOTH greps return no output.
- Lambda@Edge must either call `callback(null, ...)` or return a value.
- `detail`: `"No callback(null, ...) or return statement found"` on FAIL.

---

### Step 4 — Cross-file consistency checks

After all individual file checks, run these cross-file checks:

#### CHECK CROSS-01: cloudfront import only in CFF files

For each Lambda@Edge file, verify it was NOT already flagged as `PASS` on
LE-04. (This is a redundancy check — if LE-04 passed, CROSS-01 is informational
only; if it would fail, LE-04 already caught it.)

#### CHECK CROSS-02: KVS usage matches IR

From the domain IR, check `kvs_requirements` — this is a mapping with three
boolean fields: `needs_redirects`, `needs_continent`, `needs_eu`.

- If **at least one** field is `true`:
  - At least one CFF file must contain `cf.kvs()` — FAIL if not found.
  ```bash
  grep -rn 'cf\.kvs()' "<functions_dir>"
  ```
- If **all three** fields are `false` (or the mapping is absent):
  - No CFF file must contain `cf.kvs()` — FAIL if found (unexpected KVS usage).
  ```bash
  grep -rn 'cf\.kvs()' "<functions_dir>"
  ```

`detail`: include the IR `kvs_requirements` value and the grep result.

#### CHECK CROSS-03: Lambda@Edge expected vs present

From the domain IR, check `lambda_edge` — this is a mapping with sub-fields:
`origin_request`, `origin_response`. Each is either `null`
or a non-null object.

- If **at least one** sub-field is non-null:
  - `lambda/` directory must exist and contain at least one `.js` file.
  - FAIL if lambda dir is missing or empty.
- If **all** sub-fields are `null`:
  - `lambda/` directory must be absent or empty.
  - FAIL if lambda dir contains `.js` files (unexpected Lambda generation).

`detail`: include IR `lambda_edge` value and actual files found.

---

### Step 5 — Compile results and write output JSON

Construct the output JSON per the schema in the Output JSON Schema section.

Rules:
- `overall_status`: `"FAIL"` if ANY check across ANY file has `status == "FAIL"`.
  `"PASS"` only if all checks across all files are `"PASS"` or `"SKIP"`.
- `"SKIP"` is only valid for checks that are explicitly conditional (e.g.,
  CROSS-01 when no Lambda files exist). Do NOT use `"SKIP"` to hide failures.
- Include `detail` for every FAIL. Do not leave `detail` blank on failures.
- Include the actual grep output, line numbers, byte counts, or exit codes in
  `detail` — not just "check failed".

Write the JSON to: `cloudflare-to-aws-cdn/ir/validation/js/<hostname>-v3.json`

Create the parent directory if it does not exist.

---

### Step 6 — Report outcome

After writing the JSON:

**If overall_status == "PASS"**:
```
✓ cf-cdn-js-validator V3: <hostname> — ALL CHECKS PASSED
  Files validated: <N> CloudFront Function(s), <M> Lambda@Edge
  Output: cloudflare-to-aws-cdn/ir/validation/js/<hostname>-v3.json
```

**If overall_status == "FAIL"**:
```
✗ cf-cdn-js-validator V3: FAILURE — <hostname>
  Failed checks:
    <file_relative_path> [<type>]:
      ✗ <CHECK_ID>: <description>
        Evidence: <detail>
      ✗ <CHECK_ID>: <description>
        Evidence: <detail>
  Output: cloudflare-to-aws-cdn/ir/validation/js/<hostname>-v3.json
  DO NOT PROCEED. Fix the generator (cf-cdn-tf-domain), not the generated files.
```

The FAILURE message must be unmissable. Do not bury it.

**Critical**: Do NOT offer to fix the files. Do NOT re-run the generator. Do
NOT suggest what the fix should be. Report and stop.

## Consistency with V1/V2 Validators

The output JSON format (`schema_version`, `hostname`, `timestamp`,
`overall_status`, `files[].checks[]`) is intentionally compatible with V1 and
V2 validator outputs so that downstream aggregation scripts can process all
three without branching. When reading existing V1/V2 outputs for comparison,
treat any field not present in V3 schema as ignored.
